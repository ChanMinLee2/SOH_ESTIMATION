## 1. 필터4 재설계(chg_gap_seg 행 단위) 전/후 비교

사이클 전체 단위로 NaN 처리되던 버그 있는 데이터) vs `0805_1821_p2_mlp_qfw_35%_20%`

`lr=5e-4`, split_seed=42)는 완전히 동일 — 두 run 모두 각자 새로 학습한 Phase1
게이트를 씀(낡은 게이트 재사용 없음).

### 1.1 전체 지표

| 지표 | 이전(0804) | 이후(0805) | 변화 |
|---|---:|---:|---|
| R² | 0.9463 | **0.9558** | **+0.0095** |

충전존만 보면 개선폭이 훨씬 뚜렷하다(R² 0.9275→0.9552, RMSE -21.3%, MAPE 1.351→1.283

### 1.2 데이터셋/배치별 분해 — MAPE "악화"의 정체

`test_predictions.csv`를 `cell_id` 접두사로 MIT batch2 / MIT 나머지 / HUST로 나눠
재집계:

| 그룹 | 표본 비중 | MAPE(이전→이후) | RMSE(이전→이후) |
|---|---:|---|---|
| **MIT batch2**(고친 대상) | 4.7% | **3.22%→1.51%** | 0.0431→0.0168 |
| MIT 나머지(무관) | 27.9% | 0.95%→1.17% | 0.0127→0.0140 |
| HUST(무관) | 67.4% | 1.24%→1.33% | 0.0138→0.0148 |
| 전체 | 100% | 1.2497%→1.2971% | 0.01614→0.01465 |

**원인 분석**:
1. batch2는 극적으로 개선됐다(수정 대상이니 당연).
2. **안 건드린 MIT 나머지·HUST가 둘 다 소폭 악화**됐다 — Phase1 게이트를 매번
   새로 학습하기 때문에, batch2의 충전존이 정보량0→진짜 신호로 바뀌면서 **전역
   공유 게이트(어떤 HI를 쓸지)가 재배분**돼 다른 셀·존에 살짝 손해를 준 것으로
   보인다(멀티태스크/공유표현 학습의 전형적 트레이드오프 — 확정은 아니고 가설).
3. **RMSE는 개선인데 MAPE는 악화로 보이는 이유**: RMSE는 오차 제곱평균이라 batch2의
   예전 거대 오차(4.3%대)가 원래 전체를 크게 끌어올리고 있었다 — 그게 사라지니
   RMSE는 확실히 개선. 반면 MAPE는 표본별 %오차의 단순평균이라, batch2는 표본의
   4.7%뿐이라 거기서 아무리 크게 개선돼도(1.7%p) 기여가 작고, 나머지 95.3%의 작은
   악화(+0.1~0.22%p)가 훨씬 많은 표본에 걸쳐 있어 합이 더 크다.
   가중평균 검산: batch2 개선이 절약한 양(~26,575) < MIT나머지+HUST 악화가 추가한
   양(~42,282) → 순증가 +0.047%p(1.2497→1.2971), 실측과 정확히 일치.

**결론**: 성능이 나빠진 게 아니라, RMSE(소수의 큰 오차에 민감)와 MAPE(다수의 작은
오차에 민감)가 같은 결과를 반대 방향으로 요약해서 보여준 것 — R²/RMSE 기준으로는
명백한 개선이다.

### 1.3 정보량 0 세그먼트의 명시적 제외 (`5_model/datasets/segment_dataset.py`)

`chg_gap_seg` 수정으로 정보량0 비율이 11.33%→0.69%까지 줄었지만 **0으로 완전히
없어지지는 않았다** — `3_integrity/audit_zero_info_hi_segments.py`로 실제 학습 입력
(`_4_data_hi/q_frac_wide/n1-35%_n2-20%_N-4/seg/MIT/*.pkl`)을 직접 센 결과, MIT
588,024개 세그먼트 행 중 **4,083개(0.69%)가 여전히 HI 66개 전부 NaN**이다(배치별:
b1 1.15%, b2 1.27%, b3 0.005% — b3만 사실상 해결됨). 원인은 `chg_gap_seg`뿐 아니라
`hi_correlation.py`가 애초에 HI 계산 자체를 건너뛰는 다른 경우(예: 충전 데이터 부족으로
`q_tc < cap × 0.6`인 `_chg_incomplete` 판정)도 있어, 필터4 재설계만으로는 완전히
없앨 수 없는 잔여분이다.

이 잔여분을 처리하기 위해, `chg_gap_seg` 수정과 함께(§1.1/§1.2와 같은 시점) 데이터
**로딩 단계에서 이런 세그먼트를 아예 제외**하도록 `segment_dataset.py`를 고쳤다 —
`load_dataset_wide()`/`load_dataset_native_seg()` 양쪽 경로 모두 동일 정책:

```python
_hi_cols = [f"hi_{i:02d}" for i in range(N_HI)]
combined = combined.dropna(subset=_hi_cols, how="all")  # 정보량0 세그먼트 제외
```

**이전 동작**(기존 §1 비교 실험까지도 이 상태였음): `SegmentNormalizer.transform_x()`가
NaN을 z-score 평균(0)으로 채워, "입력=0벡터인데 타깃(`capacity_Ah`)은 진짜 SOH"라는
**학습이 원천적으로 불가능한 잡음 쌍**이 그대로 train/val/test에 섞여 들어갔다(라벨은
방전 기준이라 항상 정상값이라 이 잡음을 감춰버림).

**왜 부작용이 없는가**: `SegmentNormalizer.fit()`이 애초에 `nanmean`/`nanstd`로 정규화
통계를 계산해 이런 행을 이미 통계 계산에서 건너뛰고 있었다(`segment_dataset.py:308-309`
부근) — 즉 이 행들을 완전히 제거해도 정규화 파라미터 자체는 달라지지 않고, 단지
"0벡터 입력·실제 타깃"이라는 학습 불가능한 쌍이 손실 계산에 더는 기여하지 않게 될
뿐이다. `chg_gap_seg` 재설계가 "얼마나 많은 세그먼트가 이 상태에 빠지는가"를 줄이는
**예방** 조치였다면, 이 dropna 필터는 "그래도 남는 건 아예 학습에서 빼버리는"
**사후 청소** 조치로, 같은 문제(잘못된/정보 없는 HI가 학습에 잡음으로 섞이는 것)를
서로 다른 두 층위에서 함께 해결한 셈이다.

## 2. q_frac_ref n2/n_samples 스윕 3종

**공통 설정**: axis=q_frac_ref, n1=0.35, ref_lag=0, noise_amp=3%, noise_mode=ou,
noise_period=200(모두 기본값·동일). n2(세그먼트 길이)와 n_samples(구간당 개수)만
다르다. 세 run 모두 각자 새 Phase1 게이트로 학습.

| run | n2 | n_samples | 데이터 경로 |
|---|---:|---:|---|
| `0806_0010` | **20%** | 4 | `n1-35%_n2-20%_N-4_lag-0_noise-3%_ou-200` |
| `0806_0235` | **9%** | 4 | `n1-35%_n2-9%_N-4_lag-0_noise-3%_ou-200` |
| `0806_1352` | **5%** | **7** | `n1-35%_n2-5%_N-7_lag-0_noise-3%_ou-200` |

### 2.1 전체 지표 — 세그먼트가 짧아질수록 뚜렷하게 나빠짐

| run | R² | RMSE | MAPE |
|---|---:|---:|---:|
| 0010 (20%) | **0.9489** | 0.01574 | 1.266 |
| 0235 (9%) | 0.8883 | 0.02328 | 1.751 |
| 1352 (5%, N=7) | **0.7487** | 0.03295 | 2.433 |

n_samples를 4→7로 늘려 세그먼트 개수를 보충했음에도, 세그먼트 자체가 짧아지는
정보 손실을 못 막았다.

### 2.2 데이터셋별

| run | MIT R² | HUST R² |
|---|---:|---:|
| 0010 | 0.906 | 0.947 |
| 0235 | 0.838 | 0.876 |
| 1352 | 0.660 | 0.721 |

HUST가 세 run 모두 MIT보다 0.04~0.06 높다(표본 수가 약 2배 많은 것과 관련 가능).
하락폭 자체는 MIT/HUST 둘 다 비슷한 비율로 같이 무너진다 — 특정 데이터셋만의
문제가 아니라 세그먼트 길이 자체의 구조적 한계.

### 2.3 시나리오별 — 존별 격차가 급격히 벌어짐

- **0010(20%)**: 6개 존 R² 0.935~0.963로 고르게 양호.
- **1352(5%, N=7)**: `dis_hi`는 R²=0.871로 버티지만, **`dis_mid`=0.626, `chg_mid`=0.684**
  로 급락. `chg_mid`는 표본 수도 n=12,132로 다른 존(~55,000)의 4분의 1 — 세그먼트가
  5%로 짧아지며 `min_pts` 생존 기준 미달로 그 존의 사이클이 대거 탈락한 것(§4.4
  min_pts 절벽과 같은 현상).

### 2.4 해석

세그먼트가 짧아질수록 세그먼트 하나의 실측 포인트 수가 줄어 HI 통계량(dV/dQ 기울기,
ICA 피크 등)이 노이즈에 취약해진다. `n_samples` 증가로 세그먼트 개수를 보충해도
개별 세그먼트의 정보 손실을 상쇄 못 하고, 오히려 `min_pts` 미달로 특정 존(`mid`
계열)이 표본에서 통째로 빠지는 부작용까지 생겼다. **20%(0010)가 지금까지 가장
안정적** — 5%까지 줄이는 건 명확한 손해.

## 3. 다음 테스트 방향 제안

1. **n2를 20%보다 크게도 스윕**(예: 25%, 30%, 35%) — 지금까지 20%/9%/5% 세 점만
   봤고 전부 20% 이하였다. 20%가 로컬 최적인지, 더 키우면 계속 좋아지는지 아직
   모른다 — 방향을 반대로도 확인해야 진짜 최적 n2를 안다.
2. **q_frac_ref의 본 실험 — lag 스윕**(`docs/SOC.md` §4.1.2/§6 Phase 5): 지금까지
   전부 `ref_lag=0`(=q_frac_wide와 사실상 동등)만 봤다. `ref_lag`를 1, 그리고 §4.1.2
   표의 실측 기반 지점들(용량손실 1%/2%마다 갱신에 해당하는 사이클 수, 고정
   50/100/200사이클)로 올려가며 R²/RMSE/MAPE가 어떻게 변하는지 — 이게 q_frac_ref
   축이 존재하는 근본 이유이므로 다음 실험의 최우선 순위로 제안.
3. **permutation ablation**(§6 Phase 5): 레퍼런스를 셀 간 무작위로 섞어서 성능
   하락폭을 측정 — 모델이 세그먼트 내용물이 아니라 레퍼런스가 암시하는 위치에
   얼마나 기대는지 정량화. lag를 올리기 전에 lag=0에서 먼저 해보면, "이미 지금도
   레퍼런스에 과의존하는가"의 기준선을 잡을 수 있다.
4. **noise_amp 강건성 스윕**(§6 Phase 5): 0%→±5%로 스윕해 노이즈 민감도 곡선 확보.
5. 매 비교마다 **§1.2처럼 배치/데이터셋별 분해를 표준 절차로 고정** — 오늘처럼
   전체 지표(특히 MAPE)만 보면 실제로는 없는 "악화"로 오독할 수 있다는 게
   실증됐다.

## 4. 제안하는 진단 플랏

1. **SOH-true 구간별 오차 곡선**(x=soh_true 10분위, y=구간별 MAPE·RMSE, 두 run
   겹쳐그리기): §1.2에서 설명한 "RMSE는 개선·MAPE는 악화로 보이는" 현상을 숫자
   표 대신 한눈에 보여준다 — 앞으로 모든 전/후 비교에 기본으로 넣을 것을 제안.
2. **배치/서브그룹별 막대그래프**(x=b1/b2/b3/HUST 1-~10-, y=R²·RMSE·MAPE, run별
   색상 구분): 오늘 `cell_id` 접두사로 수동 분해했던 걸 매번 반복하지 않도록
   재사용 가능한 스크립트로 만들 것을 제안(`3_integrity/` 산하).
3. **n2 스윕 곡선**(x=n2%, y=R²/RMSE/MAPE, 데이터셋별 색상 분리, 존별 서브플롯):
   지금은 표로만 있는 2절 결과를 곡선으로 — n2를 더 넓게 스윕한 뒤(제안1) 로컬
   최적점을 시각적으로 확인.
4. **lag 스윕 곡선**(x=ref_lag 또는 그에 대응하는 "용량손실%", y=R²/RMSE, lag=0과
   lag=∞(`q_abs`) 양끝을 기준선으로 표시): §1.4의 "정합성 개선 vs 얽힘 부풀림"
   트레이드오프를 실측으로 확인하는 이 프로젝트의 핵심 그림 — 제안2(lag 스윕
   실험)의 직접적 산출물.
5. **scatter(true vs pred), 배치별 색상 구분**: 어느 배치가 어느 방향으로 편향돼
   있는지(과대/과소추정) 한눈에 확인 — 특히 lag를 올렸을 때 knee-point 이후
   구간에서 편향이 커지는지(§4.4) 확인하는 용도로 lag 스윕과 함께 쓸 것을 제안.
