## 2. Oracle 기준 성능 비교 (신뢰 가능 — 주 지표, m=10 재학습 반영 완료)

Oracle = 정답 `seg_idx`로 라우팅(분류기 오차를 배제한 회귀 헤드/CNN 융합 자체의 상한
성능). `REGRESSION_UPGRADE.md` §8.7에서 이미 oracle을 아키텍처 비교의 주 기준으로 삼기로
했었는데, 이번 데이터 무결성 사고(§4)를 겪으며 그 이유가 다시 한번 실증됐다 — hard/soft는
분류기 라우팅 품질에 오염되기 쉬운 반면 oracle은 라우팅과 무관하게 안정적이다. 아래
수치는 §4.2 수정(m=10 재학습) 반영 후 최종값이다.

**개선율(%)** — `(baseline - CNN) / baseline × 100`, 양수=개선(오차 감소)·음수=악화(오차 증가):

| 축 / 모델 | RMSE 개선율 (a) | RMSE 개선율 (b) | MAPE 개선율 (a) | MAPE 개선율 (b) |
|---|---:|---:|---:|---:|
| qfw + mlp | -14.1% | -16.6% | -18.3% | -24.4% |
| qfw + transformer | +0.3% | -0.7% | -5.0% | -4.5% |
| qfw + resnet_tab | -0.7% | **+4.0%** | -1.5% | **+5.0%** |
| vqslope + mlp | **-22.5%** | +3.2% | **-59.2%** | -1.2% |
| q_abs + mlp | -0.8% | **+4.3%** | -8.2% | +0.04% |
| **평균** | **-7.6%** | **-1.1%** | **-18.4%** | **-5.0%** |

**RMSE만 봤을 때보다 MAPE까지 같이 보면 그림이 더 나빠진다.** 두 지표가 같은 방향을
가리키는 조합(qfw+resnet_tab의 (b), q_abs+mlp의 (b) 등 근소한 개선)도 있지만, 평균으로
보면 RMSE 개선율((a) -7.6% / (b) -1.1%)보다 MAPE 개선율((a) -18.4% / (b) -5.0%)이
두 옵션 다 더 크게 나쁘다 — **CNN 융합이 절대 오차(RMSE, Ah 단위)보다 상대 오차(MAPE,
%)를 더 크게 악화시킨다**는 뜻이다. 특히 vqslope+mlp의 (a)는 RMSE 개선율(-22.5%)도 이미
나쁘지만 MAPE 개선율은 -59.2%로 훨씬 극단적이다 — MAPE는 참값이 작은 샘플(수명 후반,
용량이 많이 빠진 사이클)에서 오차가 비율로 크게 잡히는 지표라, **CNN 융합으로 생긴 추가
오차가 저용량(열화가 많이 진행된) 구간에 불균형하게 몰려 있다**는 신호로 해석할 수 있다
— 정작 실사용에서 SOH 추정이 가장 중요한 구간(수명 말기)에서 CNN 융합의 악영향이 더
크다는 뜻이라 RMSE만 보고 "약간 나쁜 정도"로 넘길 사안이 아니다.

**결론 (검증1/검증2 판정)**:
1. **검증2(시나리오 축 불문 일관된 개선)는 기각** — 축마다 부호와 크기가 다르다(qfw+mlp/
   vqslope+mlp는 뚜렷이 악화, qfw+transformer/resnet_tab은 거의 중립, q_abs+mlp는
   (b)에서만 소폭 개선). "raw 곡선 융합이 축과 무관하게 일관되게 좋다"는 가설은 데이터로
   지지되지 않는다.
2. **검증1(회귀 모델 불문 일관된 개선)도 기각** — qfw 축 안에서도 mlp가 가장 크게
   악화되고(-0.0151~-0.0180) transformer/resnet_tab은 거의 중립(-0.0008~+0.0042).
   "raw 곡선 융합이 회귀 헤드 종류와 무관하게 좋다"도 지지되지 않는다.
3. **(a) frozen reuse는 5개 조합 중 4개에서 (b) separate보다 같거나 나쁘다**(qfw+transformer만
   근소하게 역전) — 평균 Δ -0.0125 vs +0.0006. **분류기 목적(시나리오 분류)으로 학습된
   CNN 임베딩을 회귀 목적에 그대로 재사용하는 것은 오히려 손해**라는 뜻으로 해석된다 —
   분류기가 유지하려는 표현과 회귀(정밀한 용량값)가 필요로 하는 표현이 다르기 때문일
   가능성이 높다.
4. **(b) separate training은 R²/RMSE 기준으로는 평균적으로 거의 중립**(R² Δ+0.0006,
   RMSE 개선율 -1.1%)이지만 **MAPE까지 같이 보면 평균 -5.0%로 살짝 더 나쁜 쪽에 가깝다**
   (위 개선율 표). 확실한 개선이라 부르긴 어렵다. vqslope/q_abs/resnet_tab에서는 작지만
   baseline을 넘는 반면 qfw+mlp에서는 가장 크게 진다(RMSE -16.6%, MAPE -24.4%). **"원본
   곡선 정보가 이미 계산된 HI 피처보다 유의미하게 더 많은 정보를 준다"는 애초 가설
   (REGRESSION_UPGRADE.md §0~§4)은 이번 실측으로는 뒷받침되지 않는다** — HI 피처 집합
   (148D)이 이미 원본 곡선의 핵심 정보를 상당 부분 포착하고 있어서, CNN이 추가로 뽑아내는
   정보의 한계효용이 작거나(잘하면 미세하게 긍정, 못하면 오히려 노이즈로 작용)라는 그림에
   가깝다.
5. **MAPE 기준 악화 폭이 RMSE보다 항상 크거나 같다**(평균 (a) RMSE -7.6% vs MAPE -18.4%,
   (b) RMSE -1.1% vs MAPE -5.0%) — CNN 융합의 손해가 절대 오차보다 상대 오차, 즉 저용량
   (수명 후반) 구간에서 더 크게 나타난다는 뜻이다. 자세한 내용은 §2 개선율 표 아래 설명
   참고.

## 3. Hard/Soft 라우팅 지표 (m=10 재학습 반영 — 최종)

8개 run 재학습(§4.2)이 모두 성공(exit=0)해 hard/soft/clf_acc/avg_cost를 최종 수치로

전부 0.07% 이하로 떨어졌다(버그 상태였을 때는 55~172%까지 치솟았었다).

**hard ≈ oracle, 결론도 동일하다** — clf_acc가 baseline과 거의 같아졌으므로(0.9835~
0.9836) 분류기 라우팅 오차가 거의 없고, hard R²가 §2의 oracle R²와 소수점 셋째 자리까지
거의 일치한다. §2의 "검증1/검증2 기각, (a) frozen이 (b) separate보다 대체로 열등"이라는
결론은 hard(실배포) 기준에서도 그대로 재현된다 — 분류기 라우팅 오차가 CNN 융합의
악영향을 증폭시킬 거라 예상했던 §5의 가설은 **틀렸다**: 8개 run 전부 clf_acc가 baseline과
거의 같은 수준으로 회복된 지금은 그런 증폭 효과가 보이지 않는다(routing_gap_pct가
CNN 유무와 무관하게 전부 0.07% 이하).

**avg_cost 관련 주의(해석 시 반드시 감안할 것)**: CNN 융합 8개 run은 baseline 대비
avg_cost가 큰 폭으로 낮다(qfw+mlp 87.25→25.50, qfw+tr 93.58→36.67, qfw+res 90.08→26.83,
vqslope 90.42→29.58 — q_abs만 원래도 25.17로 동일). `avg_cost`는 `_compute_efficiency`가
Hard-Concrete L0 게이트로 실제 활성화된(0보다 큰) probe/scen HI 개수 기반으로 계산하는데
(`charge_probe_m`/`discharge_probe_m`은 후보 상한일 뿐, 그중 몇 개를 실제로 켤지는 학습된
게이트가 결정), CNN 임베딩이 상시 입력으로 주어지면 게이트가 명시적 HI를 덜 켜도 손실을
줄일 수 있어 sparsity 정규화(`lambda_l0`) 하에서 자연스럽게 더 적게 선택하는 것으로
보인다. **다만 이 지표는 raw CNN 자체의 순전파 비용(원본 V/I 시퀀스에 대한 conv 연산)을
전혀 포함하지 않는다** — `avg_cost`는 어디까지나 "실배포 시 원본 신호로부터 통계적 HI를
몇 개나 계산해야 하는가"라는 특징 엔지니어링 비용만 재는 지표이지, 전체 파이프라인
(원본 곡선 획득 + CNN 추론 포함) 비용이 아니다. 따라서 **"CNN 융합이 avg_cost를 3배
가까이 줄인다"를 곧바로 "더 저렴하다"로 해석하면 안 된다** — 명시적 HI 계산은 줄지만
그만큼(혹은 그 이상) CNN 추론이라는 별도 비용이 상시로 추가된다. ms/sample 벤치마크
(위 표)에서 CNN 포함 run이 baseline보다 오히려 빨라 보이는 것도 이 GPU 추론 시간에는
raw 곡선을 준비/전처리하는 비용이 포함되지 않기 때문일 가능성이 높다.

## 4. 데이터 무결성 이슈 2건 — 발견·원인·조치

이 문서를 준비하며 기존에 완료돼 있던 10개 실험 run(옵션 a 5개 + 옵션 b 5개)의
hard/soft/clf_acc 수치가 명백히 비정상(baseline 대비 급락, confusion matrix가 체계적으로
뒤섞임)임을 발견해 원인을 추적했다. **두 버그 모두 이 세션 이전에 이미 완료된 학습
run들에는 영향을 주지 않는다** — 새로 만든 10개 실험 run에서만 발생했다.

### 4.1 `scenario_spec.json` 저장 시점 문제 (수정·재평가 완료)

**증상**: 10개 run 전부 clf_acc가 0.47~0.67로 급락, confusion matrix가 lo↔hi 클래스가
통째로 뒤바뀐 패턴.

**원인**: `train_scr.py`가 Phase 2에서 `gates_from`이 가리키는 baseline의 spec으로
재할당하기 **전에** 먼저 생성한 (현재 코드 기준) spec을 `scenario_spec.json`으로 저장하고
있었다. 이 세션 이전에 `q_frac_wide`/`vqslope`/`q_abs`/`rcs`의 `_ROUTING` 상수가
SOC 명명 일관성을 위해 수정된 적이 있는데, baseline들은 그 수정 **이전** 코드로
학습됐다. 그 결과: 실제 모델은 baseline의 (구) routing으로 학습됐는데, 디스크에 저장된
`scenario_spec.json`은 (신) routing을 담고 있어 — `test_scr.py`가 이 파일을 읽어
평가할 때 분류기의 예측 클래스를 잘못된 테이블로 해석했다. **Oracle은 영향 없음**
(ground-truth `seg_idx`를 직접 쓰고 `spec.routing`을 거치지 않음).

**조치**:
1. `train_scr.py`: `gates_dir`/spec 재로드 로직을 `build_datasets`/`spec.save()` **이전**으로
   앞당겨, 앞으로의 모든 Phase 2 run은 저장된 spec과 실제 학습에 쓰인 spec이 항상 일치하도록
   구조적으로 수정.
2. 이미 완료된 10개 run: 각 run의 `gates_from` baseline이 갖고 있는 **원본**
   `scenario_spec.json`을 확인해 그대로 복사, `test_scr.py`로 10개 전부 재평가 완료.
   결과 clf_acc가 qfw 계열은 0.79~0.91, vqslope/q_abs는 0.98 수준으로 회복 — 그러나
   qfw/vqslope는 여전히 baseline(0.9835~0.9836)에 못 미쳤고, 이게 §4.2로 이어졌다.

### 4.2 `charge_probe_m`/`discharge_probe_m` 불일치 (수정·재학습·재평가 완료)

**증상**: §4.1 수정 후에도 qfw(mlp/tr/res)·vqslope 8개 run의 clf_acc가 baseline보다
낮게 남음(0.79~0.91 vs baseline 0.9835~0.9836). q_abs 2개 run만 baseline과 일치.

**원인**: 10개 `exp_*.yaml`을 만들 때 `classifier.charge_probe_m`/`discharge_probe_m`을
전부 `5`로 통일해서 썼는데, 실제 baseline들은 q_abs만 `5`고 **나머지 4개(qfw mlp/tr/res,
vqslope)는 전부 `10`**이었다(각 baseline의 `config.yaml`에서 직접 확인). `test_scr.py`는
분류기로 hard/soft 라우팅을 계산할 때 **현재 config의 m으로 만든 probe 마스크**를 씌운
`probe_x`를 재사용된 분류기에 입력한다(`evaluate_modes`가 평가 대상 회귀 모델 자체의
`get_probe_x`를 호출) — 그런데 그 분류기는 `train_classifier.py`가 baseline config의
m(=10)으로 학습한 것이라, m=5로 깎인(활성 5개, 나머지 5개는 인위적으로 0) `probe_x`를
받으면 자기가 학습 때 보지 못한 입력 분포를 받아 정확도가 떨어진다 — 정확히 관찰된
패턴과 일치.

**왜 재평가만으론 못 고치나**: 이 m은 회귀 헤드 자체의 `probe_x` 구성에도 쓰이고, Phase 2
학습 자체가 이 m으로 되어 있었다(10개 실험 모두 학습 시점부터 m=5로 진행됨). 지금 평가
시점의 m만 10으로 올리면 회귀 헤드 입장에서는 학습 때 한 번도 값을 받아본 적 없는
나머지 5개 슬롯에 실제 값이 들어가는 새로운 불일치가 생겨 오히려 더 나빠진다. **Phase 2를
m=10으로 처음부터 다시 학습해야** 분류기·회귀 헤드 양쪽이 다시 일관된다.

1. 영향받는 8개 `exp_*.yaml`(qfw mlp/tr/res × a/b, vqslope × a/b)의

## 5. 종합 결론

1. **raw CNN 융합(원본 V/I 곡선을 회귀 헤드에 추가 입력)은 이번 5개 축×모델 조합, 2개
   구현 방식(frozen reuse / separate training) 어느 쪽으로도 일관된 성능 개선을 보이지
   못했다.** 검증1(회귀 모델 불문)·검증2(시나리오 축 불문) 가설 둘 다 기각.
2. **분류기용으로 학습된 CNN을 얼려서 회귀에 재사용(a)하는 건 명확히 손해**(평균 oracle
   Δ -0.0125, hard 기준도 동일한 방향) — 목적이 다른 표현을 그대로 갖다 쓰는 데서 오는
   구조적 한계로 해석된다.
3. **회귀 전용 CNN을 처음부터 같이 학습(b)해도 평균적으로는 거의 중립**(oracle Δ +0.0006)
   — qfw+mlp에서는 오히려 가장 크게 지고, vqslope/q_abs/resnet_tab에서만 소폭 이긴다.
   기존 148D HI 피처가 원본 곡선의 유용한 정보를 이미 상당히 포착하고 있어 CNN이 추가로
   뽑아내는 한계효용이 작다는 그림과 일치한다.
4. **hard(실배포) 기준도 oracle과 같은 결론**(§3) — clf_acc가 baseline 수준으로
   회복된 뒤에는 라우팅 오차가 CNN 융합의 악영향을 증폭시키는 효과가 관측되지 않았다.
5. **avg_cost 하락(§3 주의사항)을 "효율 이득"으로 오독하지 말 것** — CNN 자체의 추론
   비용이 그 지표에 반영돼 있지 않다.
6. **권고**: 현재 형태의 raw CNN 융합(방안2, `REGRESSION_UPGRADE.md` §4)을 프로덕션에
   채택할 근거는 이번 실측으로는 부족하다. 이번 결과가 "HI 피처 집합이 이미 충분하다"는
   뜻인지 "CNN 아키텍처/학습 방식이 이 데이터 규모에 안 맞는다"는 뜻인지는 구분이 안
   되므로, 후속으로 시도해볼 만한 방향은 (i) CNN을 더 강한 정규화·데이터 증강과 함께
   학습, (ii) HI 피처 없이 CNN 임베딩만으로 회귀(현재 HI의 정보 상한을 CNN이 실제로
   넘어서는지 직접 확인), (iii) CNN 브랜치에도 L0/게이트를 씌워 head가 필요할 때만
   쓰도록 유도 — 정도이나, 이번 세션 범위에는 포함하지 않는다.
