# v5 설계안 — v4 + raw HI 그룹 게이팅

작성일: 2026-09-01 · 전제: `docs/260827_RESULTS.md`(v0~v4/ctrl 실측), `docs/260901_REPORT.md`
"향후 방향" 절의 v5 아이디어를 구체화한 문서. **아직 미구현 — 설계만.**

---

## 1. 왜 v5인가

- v0-ctrl 실측(3-seed): 그룹 게이팅(`GroupedHardConcreteGate`)은 **성능은 안 바꾸지만
  시드 간 선택 안정성은 뚜렷이 올린다**(τ 0.1184 vs 0.1029, `docs/260827_RESULTS.md`
  "v0-ctrl 정식 학습 결과" 절).
- 그런데 v0~v4 중 이 메커니즘을 실제로 쓰는 건 **v0(와 v0-ctrl)뿐**이다. v1~v4는
  `--kernel-features-pkl`을 쓰는 순간 `--synergy-groups-json`과 argparse에서부터
  상호배타라(`phase1_trainer_v2.py`), raw HI 64개가 전부 완전히 독립된 게이트다.
- 특히 v3/v4가 만든 다중공선성 덩어리(예: dis_hi 4+25=29개)는 여전히 raw HI 레벨에서
  아무 조율 없이 29개가 각자 게이트를 다툰다 — v0-ctrl이 증명한 "그룹화의 시드 안정화
  효과"를 이 덩어리들에 적용 안 하고 있는 셈.
- **v5 = v4(커널+시나리오 특이/공유 분류)에, raw 블록 중 "특이(specific)" 39개에만
  그룹 게이팅을 추가한 버전.**

## 2. 핵심 설계 결정 두 가지

### 2-1. 그룹 게이팅은 공유(25개)가 아니라 특이(39개)에만 적용한다

공유 HI 25개는 이미 `shared_gate` 하나로 완전히 묶여있다(v0의 그룹 게이팅보다 더 강한
형태의 "그룹화" — 25개가 아예 게이트 파라미터 자체를 공유). 여기에 또 그룹 게이팅을
얹는 건 의미가 없다. 반대로 특이 39개는 지금 v4에서도 완전히 독립 게이트라 — v0-ctrl이
보여준 이득을 볼 여지가 남은 쪽은 여기뿐이다.

### 2-2. group_id는 "성장 그룹"이 아니라 "연결요소(survivor+attached)" 기준으로 만든다

이전 검토(이 세션)에서 확인한 결정적 이유: `GroupedHardConcreteGate`의 설계 전제는
"그룹 멤버는 그래디언트가 서로 비슷하다"(다중공선성 있는 애들끼리 묶어야 의미가 있음)
인데, v3의 "성장 그룹"(`seg_s_groups`)은 정반대로 **서로 다른 연결요소에서 뽑은,
일부러 상호보완적인(비중복) 조합**이다. 이걸 그대로 group_id로 쓰면 전제가 깨진다.
올바른 단위는 **연결요소**(`seg_s_groups[gi]` + `seg_s_group_attached[gi]`를 합친 것,
즉 진짜 서로 `|corr|>=0.9`인 애들끼리만 묶은 것)다.

## 3. 구현 상세

### 3-1. `scr_model.py` — 사실 거의 다 돼있다

`SCRModel.__init__`을 직접 읽어보니(105~129번째 줄), `shared_hi_mask`가 주어지면
`scen_gate_width = len(specific_idx)`(=39)로 이미 좁혀지고, 그 폭으로 `scen_gates`를
만들 때 `scen_group_ids`가 있으면 `GroupedHardConcreteGate(scen_gate_width,
scen_group_ids[s])`를 쓰도록 **이미 짜여 있다**:

```python
if scen_masks is None:
    scen_group_ids = scen_group_ids or {}
    self.scen_gates = nn.ModuleList([
        GroupedHardConcreteGate(scen_gate_width, scen_group_ids[s]) if s in scen_group_ids
        else HardConcreteGate(scen_gate_width)
        for s in range(self.n_scenarios)
    ])
```

막고 있는 건 딱 한 줄뿐이다:

```python
if shared_hi_mask is not None and scen_group_ids:
    raise ValueError("shared_hi_mask와 scen_group_ids는 동시 사용을 지원하지 않습니다 "
                      "(그룹 게이팅 + 공유/시나리오별 분리 조합은 스코프 밖).")
```

**즉 필요한 변경은 이 가드를 지우는 것 하나뿐**(+ `scen_group_ids[s]`의 길이가
`scen_gate_width`(39)와 정확히 맞아야 함 — 이건 3-2가 책임진다). `_gate_saturation_fraction`
등 나머지 코드는 `GroupedHardConcreteGate`가 `HardConcreteGate`를 상속해 `gate_prob()`을
그대로 쓰므로 손댈 필요 없다(v0에서 이미 검증된 경로).

### 3-2. 새 스크립트 — 연결요소를 specific-39로 필터링한 group_ids 생성

기존 `_load_synergy_group_ids`(train_scr.py)는 그룹 원소 합이 정확히 64여야 하므로
그대로 못 쓴다(v3 json은 growth 멤버만 합쳐 64가 안 됨 — 이전에 확인된 크래시 원인).
새 로직이 필요:

1. `synergy_groups_..._v3.json`에서 시나리오별 `seg_s_groups[gi] + seg_s_group_attached[gi]`를
   합쳐 "연결요소" 리스트 복원(멤버 인덱스 0~63 전체를 커버).
2. `hi_scenario_interaction_..json`의 concept별 `significant` 플래그로 공유(25)/특이(39)
   판정(시나리오 무관, concept 레벨 — v4가 이미 쓰는 것과 동일 소스).
3. 각 연결요소를, 특이 39개에 속하는 멤버만 남기고 필터링(공유 멤버는 버림 — 어차피
   `shared_gate`가 담당). 필터링 후 크기가 1이면 사실상 "그룹 없음"과 동일.
4. `SCRModel`의 `_specific_idx = torch.nonzero(~shared_hi_mask)`와 **정확히 같은 정렬
   순서**로 39개를 나열하고, 그 순서 그대로 로컬 group_id(0..n_local_groups-1)를 부여.
5. 출력: `{scenario_idx: [group_id per specific-idx 순서, 길이 39]}` — 새 스크립트
   (가칭 `build_component_groups.py`, 또는 `build_synergy_groups.py`에 `--for-specific
   --interaction-json` 모드 추가)로 저장.

### 3-3. `phase1_trainer_v2.py` — 새 CLI 플래그

`--synergy-groups-json`(v0 전용, 64 전체)과 이름이 겹치면 안 되므로 별도 플래그
(가칭 `--specific-group-ids-json`) 신설. `--interaction-json`과는 **함께 써야** 하고
(둘 다 shared/specific 분리가 전제), `--synergy-groups-json`과는 여전히 상호배타.
`--kernel-features-pkl`은 그대로 필요(v5도 v3 커널 재사용).

```
python 5_model/experiments/phase1_lab/phase1_trainer_v2.py \
    ... (v4와 동일 인자) \
    --interaction-json .../hi_scenario_interaction_k25_full_N2.json \
    --specific-group-ids-json .../specific_component_groups_k25_full_N2.json \
    --tag p1v5_full
```

## 4. 검증 계획 — v5-ctrl 없이는 신뢰 불가

이 세션 전체가 반복해서 보여준 교훈: "의미 기반으로 묶었다"는 것 자체의 이득은
무작위 대조군 없이는 판단할 수 없다(v0 vs v0-ctrl, v2 vs v-ctrl 전부 이 검증 없이는
결론이 뒤집혔다). v5도 동일하게:

- **v5**: 위 3-1~3-3대로, 연결요소 기준 그룹.
- **v5-ctrl**: 특이 39개는 그대로 두고, 그 39개 안에서 그룹 크기 분포만 보존한 채
  멤버를 무작위 재배정(`build_groups_shuffled`류 로직 재사용 가능 — 이미 v-ctrl에서
  검증된 패턴).
- 비교 지표는 기존과 동일: 시드 간 τ/Jaccard(주 지표 — 이게 오르는지가 핵심 가설),
  val R²(변화 없을 것으로 예상, 안 바뀌면 오히려 좋은 신호), 시나리오 간 τ(참고용).

**기대 결과**: 성능(R²)은 거의 안 바뀌고, 특이 39개만 놓고 본 시드 간 τ가 v4보다
오르면(그리고 v5-ctrl보다도 오르면) 가설(연결요소 기준 그룹화가 진짜 안정성을 준다) 확인.
v5-ctrl과 차이가 없으면 "그룹화 자체의 기계적 효과"로 결론 나는 거고, 이 경우도
v0-ctrl 때와 마찬가지로 의미 있는 결과다.

## 5. 리스크 / 열린 질문

- **raw 블록은 여전히 예측의 2~11%(lambda 설정별)만 차지한다** — 그룹화를 아무리 잘해도
  체감 효과는 raw-kernel 양극화가 해결되기 전까지 제한적일 수 있다. 순서상 raw-kernel
  양극화 해결과 병행하거나 그 이후가 나을 수 있음(`docs/260901_REPORT.md` "향후 방향" 참고).
- **연결요소 크기가 시나리오마다 매우 불균등하다**(dis_hi 29개 vs chg_hi 최대 4개) —
  특이-39로 필터링하면 이 불균등이 어떻게 바뀌는지 사전에 한 번 찍어봐야 한다(어떤
  시나리오는 필터링 후 그룹이 거의 안 남을 수도 있음).
- **`--specific-group-ids-json`의 정렬 순서 버그 위험**: `_specific_idx`와 순서가
  1개라도 어긋나면 조용히 엉뚱한 HI를 엉뚱한 그룹으로 묶는 채로 학습된다(에러 없이
  "그럴듯하게" 돌아감) — 구현 후 반드시 이름 대조 방식의 sanity check 스크립트를 먼저
  돌려서 검증할 것(예: group_ids[i]가 가리키는 그룹의 다른 멤버들과 HI i가 실제로
  `|raw corr|>=0.9`인지 역으로 재확인).

## 6. 작업 순서 제안

1. sanity check용 소규모 스크립트로 "연결요소→specific 필터링" 로직을 먼저 검증(3-2,
   3번 리스크 항목 먼저 해소).
2. `scr_model.py`의 가드 한 줄 제거 + 간단한 단위 테스트(shared+group 동시 지정 시
   forward가 죽지 않고 shape이 맞는지).
3. `phase1_trainer_v2.py` CLI 플래그 추가.
4. v5 1-seed(42) smoke test → v5-ctrl 1-seed → 방향성 확인되면 3-seed로 확장.
5. 우선순위는 v4-ctrl seed=123 완료, raw-kernel 양극화 해결 착수 **이후**로 권장
   (지금 열려있는 항목과 동시에 벌이면 원인 분리가 또 어려워짐).
